# Release Rules

本项目使用 `MAJOR.MINOR.PATCH` 版本号，`package.json` 的 `version` 是版本唯一来源。

即使项目仍处于 `0.x` 阶段，也按稳定语义判断版本变化，不把 `0.x` 作为任意破坏兼容的理由。

## 版本判断

### PATCH

修复已有功能或做小范围行为调整时更新 `PATCH`。

示例：

- bug 修复
- UI 细节优化
- 文案调整
- 拖拽、点击、提示时间等已有功能的行为修正
- 内部实现调整，但不改变用户数据结构

### MINOR

新增用户可见能力，且保持向后兼容时更新 `MINOR`。

示例：

- 新增设置项
- 新增文件夹功能
- 新增导入、导出或备份能力
- 新增 UI 入口
- 新增兼容性策略
- 新增存储字段，但旧数据仍可正常读取

### MAJOR

引入破坏性变化或有用户数据兼容风险时更新 `MAJOR`。

示例：

- 存储格式不兼容
- 导入导出格式不兼容
- 删除已有用户功能
- 用户数据需要迁移且存在失败风险
- 扩展权限明显扩大
- 不再支持已声明支持的浏览器或页面形态

## 可以不更新版本的情况

以下变更可以不更新版本，但提交前仍需明确判断：

- 只改测试
- 只改开发文档
- 只改注释
- 未提交的临时调试改动
- 构建产物变化但源码没有变化

如果文档变化对应用户可见功能边界、存储格式、备份策略或支持平台变化，应跟随对应功能版本一起更新。

## 提交流程

每次运行时代码修改后，提交前按顺序完成：

1. 判断版本类型：`patch`、`minor`、`major` 或 `no-version`
2. 需要更新版本时修改 `package.json`
3. 用户可见变化写入 `CHANGELOG.md`
4. 涉及功能边界、数据格式、存储 key、备份策略或支持平台时更新 `README.md`
5. 涉及开发规则、目录约束、验证命令或架构边界时更新 `AGENTS.md`
6. 运行 `bun run typecheck`
7. 运行 `bun run test`
8. 运行 `bun run build`
9. 再提交 Git

## Changelog 规则

`CHANGELOG.md` 使用倒序记录，最新版本在最上方。

未发布的运行时代码改动先放入 `Unreleased`。发布或提交版本更新时，将 `Unreleased` 内容移动到目标版本号下。

建议分类：

- `Added`：新增功能
- `Changed`：行为变化
- `Fixed`：问题修复
- `Removed`：删除功能

分类不需要为了形式强行保留。没有内容的分类应删除。
